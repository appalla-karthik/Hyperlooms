# Hyperlooms Provider Agent

The provider agent is the only Hyperlooms component intended to run directly on a contributor machine. The intended customer delivery model is **installable host software**, not a remotely hosted web service that somehow controls their GPU. The agent will run as a background service on a supported Linux NVIDIA host; its embedded browser console is a local UI for that installed software. The separate Hyperlooms web dashboard and control plane are hosted services. A signed installer, automatic updates, and a first-run enrollment experience remain future work; the current Go process and systemd template are not a finished customer package.

The agent retains configuration, structured logging, graceful shutdown, version reporting, and local health endpoints. Its embedded provider console is available at `http://127.0.0.1:9091/` by default. It shows live connection state, heartbeat times, NVIDIA GPU discovery, diagnostics, and a bounded local activity history without reading terminal logs. `/api/status` is a read-only JSON view. The console and JSON endpoint reject non-loopback peers and non-loopback Host headers even if health checks bind to a wider interface.

The console checks local NVIDIA hardware independently of enrollment, then refreshes that inventory every minute. With `HYPERLOOMS_AGENT_GRPC_ADDRESS`, all certificate/node settings, and an absolute private `HYPERLOOMS_AGENT_STATE_DIR` provided, the agent opens an outbound mTLS gRPC session, sends a capability hello, and continues heartbeats. A heartbeat can carry an issued-lease transport offer; the agent checks node/GPU identity, IDs, token, and expiry, syncs a local receipt journal, then sends a receipt. When the control plane's default-off command-staging gate is explicitly enabled, a later heartbeat can deliver the pinned command. The agent requires a confirmed matching lease receipt, validates and syncs the command, and acknowledges staging. With the separate input-read gate enabled, it checks bounded chunk order, length, SHA-256 and JSON for the fixed `request.json`. With `HYPERLOOMS_AGENT_EXECUTION_ENABLED=true` on both ends, the Linux amd64 worker persists a one-shot execution marker, obtains fenced start authorization, runs a digest-pinned approved image in restricted Docker, renews the lease, and uploads a bounded result. All gates default off; execution additionally requires runtime recovery, server-side lease-expiry reconciliation, and requester storage. A corrupt, foreign-node, or unsafe journal prevents connection, and a reconnect never silently replays work. This remains **not** a safe public-provider release: production certificate issuance, host/image qualification, complete remote-job acceptance, and crash/recovery testing are still open. Reported GPUs stay offline and unschedulable until a trusted operator verifies and enables them. The embedded console is observational, not an enrollment or workload-control UI.

```powershell
go run ./cmd/hyperlooms-agent
go run ./cmd/hyperlooms-agent version
go run ./cmd/hyperlooms-agent preflight
go test ./...
```

`preflight` is a read-only host-prerequisite report and needs no enrollment credentials. On the initial supported platform (Linux amd64), it checks NVIDIA GPU discovery and the Docker server platform. It exits `0` only when these limited prerequisites are observed; an unsupported or incomplete host exits `1` and still prints JSON. A passing report **does not** prove the Docker daemon is local, NVIDIA Container Toolkit can inject the GPU, the restricted container can run, or cleanup works. Do not enable runtime recovery or accept public workloads based on this command alone. Run it as the same OS user that will run the service, then complete the witnessed host smoke described in the Phase 1 roadmap. On Linux ARM64, `preflight` now shows Jetson Nano/L4T diagnostics, but always exits `1` with zero schedulable GPUs; it does not run CUDA or Docker containers. The [Jetson host survey](../../docs/development/jetson-host-survey.md) records the actual device evidence and remaining gates.

The operator has now reported CUDA kernel passes on the Jetson host, in a root container, and in a restricted non-root NVIDIA-runtime container with cleanup. The [Jetson host survey](../../docs/development/jetson-host-survey.md) records the exact evidence and test commands. This is not a remote Hyperlooms job; ARM64 still reports zero schedulable GPUs.

To collect Jetson compatibility information without cloning the repository on that device, download and review the read-only survey script, then run it. It does not use `sudo`, start a container, or change settings:

```sh
curl -fsSLo hyperlooms-jetson-survey.sh https://raw.githubusercontent.com/appalla-karthik/Hyperlooms/main/scripts/jetson-host-survey.sh
sed -n '1,200p' hyperlooms-jetson-survey.sh
bash hyperlooms-jetson-survey.sh
```

Environment variables are documented in the repository `.env.example`.

For a manual mTLS run, set `HYPERLOOMS_AGENT_STATE_DIR` to a dedicated absolute directory writable only by the agent user. On Linux, use mode `0700`; the journal and persistent `agent.lock` file are mode `0600`. An enrolled agent holds an OS file lock for its whole process lifetime; another process using the **same state directory** cannot start a session. Do not share, rename, or delete this directory or its lock file while the agent is enrolled. Use one persistent state directory per provider node. For example, a local Windows development run could use `D:\Hyperlooms-agent-state`. The systemd template supplies `/var/lib/hyperlooms-agent` automatically. A receipt is intentionally refused while a different unexpired lease is journaled; a persisted execution attempt is never replayed after reconnect. Expiry reconciliation, rather than the agent, resolves abandoned leases.

The `containerruntime` constructs restricted Docker execution for one digest-pinned image and one NVIDIA GPU UUID on Linux amd64. It requires a canonical node ID, tags the container with exact agent/node/lease ownership labels, enforces a deadline, memory/PID limits, no container network, read-only root filesystem, non-root UID, dropped capabilities, and no privilege escalation. `Execute` verifies a Cosign keyless signature against the exact main-branch recipe workflow identity before Docker create, bind-mounts bounded verified JSON input, and permits one pre-created result file with a 4 MiB file-size limit. The host accepts at most 1 MiB of regular JSON after exit 0. Cosign and the exact signed digest must be installed/pre-pulled; execution uses `--pull=never`. The default-off session worker now invokes this path only for a confirmed staged command, then uploads the result over mTLS for server-side schema, digest, ownership, and fencing checks. Container start/wait/removal use Docker's returned full ID. `RecoverOrphans` verifies all this node's labeled containers before removing exact IDs, and runs at startup only with `HYPERLOOMS_AGENT_RUNTIME_RECOVERY_ENABLED=true` after the state lock is acquired. Recovery failure blocks startup; no real Linux amd64 Docker recovery has been witnessed. Docker daemon access is privileged, and a second agent using a different state directory for the same node is not prevented by the local lock. A supported NVIDIA host smoke, full remote-job run, restart and stop tests are still required. Jetson/ARM64 has a diagnostic CUDA container smoke but no schedulable GPU support.

For unattended Linux hosts, a hardened [systemd unit and setup notes](packaging/systemd/README.md) are provided. The unit has not yet been qualified on a real NVIDIA host; it does not replace a signed installer or first-run setup flow.

Do not use a self-signed or shared client certificate in a public network. An operator must first create a pending provider node, issue a trusted client certificate containing the URI SAN `urn:hyperlooms:provider:<node-uuid>`, and bind its exact certificate fingerprint to that node. The trusted local CLI and rotation/revocation sequence are documented in [provider identity operations](../../docs/security/provider-identity-operations.md); they are not exposed as a public API.
