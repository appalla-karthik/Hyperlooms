# HYPER_LOOMS Provider Agent

The provider agent is the only Hyperlooms component intended to run directly on a contributor machine. The intended customer delivery model is **installable host software**, not a remotely hosted web service that somehow controls their GPU. The agent will run as a background service on a supported Linux NVIDIA host; its embedded browser console is a local UI for that installed software. The separate Hyperlooms web dashboard and control plane are hosted services. A signed installer, automatic updates, and a first-run enrollment experience remain future work; the current Go process and systemd template are not a finished customer package.

The agent retains configuration, structured logging, graceful shutdown, version reporting, and local health endpoints. Its embedded provider console is available at `http://127.0.0.1:9091/` by default. It shows live connection state, heartbeat times, NVIDIA GPU discovery, diagnostics, and a bounded local activity history without reading terminal logs. `/api/status` is a read-only JSON view. The console and JSON endpoint reject non-loopback peers and non-loopback Host headers even if health checks bind to a wider interface.

The console checks local NVIDIA hardware independently of enrollment, then refreshes that inventory every minute. With `HYPERLOOMS_AGENT_GRPC_ADDRESS`, all certificate/node settings, and an absolute private `HYPERLOOMS_AGENT_STATE_DIR` provided, the agent opens an outbound mTLS gRPC session, sends a capability hello, and continues heartbeats. A heartbeat can carry an issued-lease transport offer; the agent checks node/GPU identity, IDs, token, and expiry, syncs a local receipt journal, then sends a receipt. It records the server's receipt confirmation in that journal. A corrupt, foreign-node, or unsafe journal prevents connection, rather than silently accepting fresh work. **This is durable transport bookkeeping, not an execution command: it does not download an image or start a workload.** Connection readiness is false while disconnected. Without the gRPC settings, it runs local-only. This is a Phase 1 transport increment, **not** a safe public-provider release: self-service enrollment, production certificate issuance, hardware verification, image execution, artifacts, and executable job commands are not implemented. Reported GPUs stay offline and unschedulable. A service installer and first-run setup wizard are also still pending; the embedded console currently provides observation, not credential upload or configuration mutation.

```powershell
go run ./cmd/hyperlooms-agent
go run ./cmd/hyperlooms-agent version
go test ./...
```

Environment variables are documented in the repository `.env.example`.

For a manual mTLS run, set `HYPERLOOMS_AGENT_STATE_DIR` to a dedicated absolute directory writable only by the agent user. On Linux, use mode `0700`; the journal is mode `0600`. Do not share or delete this directory while the agent is enrolled. For example, a local Windows development run could use `D:\Hyperlooms-agent-state`. The systemd template supplies `/var/lib/hyperlooms-agent` automatically. A receipt is intentionally refused while a different unexpired lease is already journaled; lease recovery and execution lifecycle are not implemented yet.

An internal `containerruntime` foundation constructs a restricted Docker execution for one digest-pinned image and one NVIDIA GPU UUID on Linux amd64. It requires a canonical node ID, tags the container with exact agent/node/lease ownership labels, enforces a lease deadline, memory/PID limits, no container network, read-only root filesystem, non-root UID, no added capabilities, and no privilege escalation. Normal start/wait/removal use Docker's returned full container ID, not a reusable name. An internal `RecoverOrphans` helper can list and verify the entire bounded set of this node's labeled containers before removing any by exact ID. It must run only during single-instance startup before new workloads; **it is not wired into startup or the agent session**, and no real Docker recovery has been tested. Older unlabeled containers are not automatically recovered. Images are not fetched or signature-verified, inputs/results and logs are not wired, and Docker daemon access itself is privileged. These gaps and a real Linux NVIDIA Container Toolkit smoke test must be closed before connecting the runtime to leases. Jetson/ARM64 requires a separate compatibility path.

For unattended Linux hosts, a hardened [systemd unit and setup notes](packaging/systemd/README.md) are provided. The unit has not yet been qualified on a real NVIDIA host; it does not replace a signed installer or first-run setup flow.

Do not use a self-signed or shared client certificate in a public network. An operator must first create a pending provider node, issue a trusted client certificate containing the URI SAN `urn:hyperlooms:provider:<node-uuid>`, and bind its exact certificate fingerprint to that node. The trusted local CLI and rotation/revocation sequence are documented in [provider identity operations](../../docs/security/provider-identity-operations.md); they are not exposed as a public API.
