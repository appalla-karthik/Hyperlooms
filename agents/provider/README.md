# HYPER_LOOMS Provider Agent

The provider agent is the only Hyperlooms component intended to run directly on a contributor machine. The intended customer delivery model is **installable host software**, not a remotely hosted web service that somehow controls their GPU. The agent will run as a background service on a supported Linux NVIDIA host; its embedded browser console is a local UI for that installed software. The separate Hyperlooms web dashboard and control plane are hosted services. A signed installer, automatic updates, and a first-run enrollment experience remain future work; the current Go process and systemd template are not a finished customer package.

The agent retains configuration, structured logging, graceful shutdown, version reporting, and local health endpoints. Its embedded provider console is available at `http://127.0.0.1:9091/` by default. It shows live connection state, heartbeat times, NVIDIA GPU discovery, diagnostics, and a bounded local activity history without reading terminal logs. `/api/status` is a read-only JSON view. The console and JSON endpoint reject non-loopback peers and non-loopback Host headers even if health checks bind to a wider interface.

The console checks local NVIDIA hardware independently of enrollment, then refreshes that inventory every minute. With `HYPERLOOMS_AGENT_GRPC_ADDRESS`, all certificate/node settings, and an absolute private `HYPERLOOMS_AGENT_STATE_DIR` provided, the agent opens an outbound mTLS gRPC session, sends a capability hello, and continues heartbeats. A heartbeat can carry an issued-lease transport offer; the agent checks node/GPU identity, IDs, token, and expiry, syncs a local receipt journal, then sends a receipt. When the control plane's default-off command-staging gate is explicitly enabled, a later heartbeat can deliver the pinned command. The agent requires a confirmed matching lease receipt, validates the command, syncs it into the same private journal, and only then sends a staging receipt. This **does not download an image, access private objects, or start a workload**. A corrupt, foreign-node, or unsafe journal prevents connection. Connection readiness is false while disconnected. Without the gRPC settings, it runs local-only. This remains **not** a safe public-provider release: self-service enrollment, production certificate issuance, hardware verification, image execution, artifact exchange, lease renewal, and runtime recovery remain open. Reported GPUs stay offline and unschedulable. A service installer and first-run setup wizard are also pending; the embedded console provides observation, not credential upload or configuration mutation.

```powershell
go run ./cmd/hyperlooms-agent
go run ./cmd/hyperlooms-agent version
go run ./cmd/hyperlooms-agent preflight
go test ./...
```

`preflight` is a read-only host-prerequisite report and needs no enrollment credentials. On the initial supported platform (Linux amd64), it checks NVIDIA GPU discovery and the Docker server platform. It exits `0` only when these limited prerequisites are observed; an unsupported or incomplete host exits `1` and still prints JSON. A passing report **does not** prove the Docker daemon is local, NVIDIA Container Toolkit can inject the GPU, the restricted container can run, or cleanup works. Do not enable runtime recovery or accept public workloads based on this command alone. Run it as the same OS user that will run the service, then complete the witnessed host smoke described in the Phase 1 roadmap. On Linux ARM64, `preflight` now shows Jetson Nano/L4T diagnostics, but always exits `1` with zero schedulable GPUs; it does not run CUDA or Docker containers. The [Jetson host survey](../../docs/development/jetson-host-survey.md) records the actual device evidence and remaining gates.

The operator has now reported CUDA kernel passes on the Jetson host, in a root container, and in a restricted non-root NVIDIA-runtime container with cleanup. The [Jetson host survey](../../docs/development/jetson-host-survey.md) records the exact evidence and test commands. This is not a remote Hyperlooms job; ARM64 still reports zero schedulable GPUs.

To collect Jetson compatibility information without cloning the repository on that device, download and review the read-only survey script, then run it. It does not use `sudo`, start a container, or change settings:

```sh
curl -fsSLo hyperlooms-jetson-survey.sh https://raw.githubusercontent.com/appalla-karthik/Hyperlooms/main/scripts/jetson-host-survey.sh
sed -n '1,200p' hyperlooms-jetson-survey.sh
bash hyperlooms-jetson-survey.sh
```

Environment variables are documented in the repository `.env.example`.

For a manual mTLS run, set `HYPERLOOMS_AGENT_STATE_DIR` to a dedicated absolute directory writable only by the agent user. On Linux, use mode `0700`; the journal and persistent `agent.lock` file are mode `0600`. An enrolled agent holds an OS file lock for its whole process lifetime; another process using the **same state directory** cannot start a session. Do not share, rename, or delete this directory or its lock file while the agent is enrolled. Use one persistent state directory per provider node. For example, a local Windows development run could use `D:\Hyperlooms-agent-state`. The systemd template supplies `/var/lib/hyperlooms-agent` automatically. A receipt is intentionally refused while a different unexpired lease is already journaled; lease recovery and execution lifecycle are not implemented yet.

An internal `containerruntime` foundation constructs a restricted Docker execution for one digest-pinned image and one NVIDIA GPU UUID on Linux amd64. It requires a canonical node ID, tags the container with exact agent/node/lease ownership labels, enforces a lease deadline, memory/PID limits, no container network, read-only root filesystem, non-root UID, no added capabilities, and no privilege escalation. Its `Execute` entrypoint now verifies a Cosign keyless signature against the exact main-branch recipe workflow identity before Docker create, requires bounded JSON input, bind-mounts a private staged file read-only, and lets the non-root container write only one pre-created result file through a bind mount and 4 MiB file-size limit. The host accepts at most 1 MiB of regular JSON after exit 0. The host must have Cosign installed and the exact signed digest pre-pulled; execution uses `--pull=never`. This is an **internal runtime path only**: the current transport offer has no executable image/input/result command, so the agent session does not invoke it. Result schema/ownership, artifact upload, logs, and fencing-aware success reporting remain unwired. Normal start/wait/removal use Docker's returned full container ID, not a reusable name. An internal `RecoverOrphans` helper lists and verifies the entire bounded set of this node's labeled containers before removing any by exact ID. Startup invokes this helper **only when** `HYPERLOOMS_AGENT_RUNTIME_RECOVERY_ENABLED=true`, after acquiring the state lock and before opening the session or local console. Recovery failure blocks startup; the flag defaults to `false` until a real Linux amd64 Docker/NVIDIA host test qualifies it. No real Docker recovery has been tested. Older unlabeled containers are not automatically recovered. Docker daemon access itself is privileged. The state-directory lock does not protect against a second agent configured with a different directory for the same node; service deployment must enforce one directory and one instance. A real Linux NVIDIA Container Toolkit smoke test remains required before connecting the runtime to leases. Jetson/ARM64 has an experimental agent build and a successful diagnostic CUDA container smoke, but no schedulable GPU support.

For unattended Linux hosts, a hardened [systemd unit and setup notes](packaging/systemd/README.md) are provided. The unit has not yet been qualified on a real NVIDIA host; it does not replace a signed installer or first-run setup flow.

Do not use a self-signed or shared client certificate in a public network. An operator must first create a pending provider node, issue a trusted client certificate containing the URI SAN `urn:hyperlooms:provider:<node-uuid>`, and bind its exact certificate fingerprint to that node. The trusted local CLI and rotation/revocation sequence are documented in [provider identity operations](../../docs/security/provider-identity-operations.md); they are not exposed as a public API.
