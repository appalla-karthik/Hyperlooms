# Phase 1 Execution Core

Phase 1 now has durable records, a transactional scheduler claim with an experimental opt-in bounded poller, a lease-expiry reconciliation transaction with a separate opt-in bounded poller, certificate-bound transport offer/receipt over mTLS, default-off prepared-command staging, and internal fenced execution-state transitions. It is not an operational GPU compute system: staged commands are never run, and remote process shutdown is not yet proven.

## Records

- `provider_nodes` stores a provider identity and enrollment/availability state. A claimed node ID must later be bound to its mTLS client certificate; an agent-supplied string is not proof of identity.
- `provider_enrollment_invites` stores a one-time, short-lived, revocable invite digest. Its 256-bit bearer token is returned only when issued, never persisted in plaintext. Redeeming it creates a `PENDING/OFFLINE` node, not a verified provider.
- `provider_certificates` binds a node to one active certificate fingerprint and, during rotation, at most one staged replacement. Binding is an operator-side expectation; the node becomes `VERIFIED/OFFLINE` only when that exact certificate is presented through an authenticated mTLS session. Revocation disables the credential and node.
- `provider_gpus` stores reported hardware separately from verification state. Reports are never schedulable solely because the agent sent them.
- `provider_gpu_reviews` keeps historical rows for a trusted operator's manual approval, binding the reported GPU attributes to an external evidence SHA-256 and reviewer subject. The service inserts rather than updates these rows; database-level immutability is not yet enforced. The digest is a reference to evidence retained outside this table, not proof that the evidence is authentic.
- `workload_recipes` identifies an OCI repository and immutable SHA-256 digest, with explicit approval and resource ceilings.
- `jobs` records the requester, recipe, state, request hash, request-contract version, input-manifest digest, and a requester-scoped idempotency key. The internal submission service now rejects a reused key with a different v1 request and returns the same job for retries. Legacy internal rows are version `0` and cannot replay as v1.
- `job_attempts` preserves each execution attempt. Retry creates a higher attempt number rather than erasing prior evidence.
- `gpu_leases` has an expiry and database-issued, monotonic fencing token. A partial unique index permits at most one active lease per `(node_id, gpu_uuid)`. A completion from an old token must later be rejected even if the old process kept running.
- `outbox_events` is written in the same transaction as initial job creation, lease claim, lease expiry, and lease receipt. No dispatcher is implemented yet.

The database also limits one active attempt per job. `SchedulerClaimService` atomically locks a queued job with `SKIP LOCKED`, checks an approved recipe and a fresh, verified, certificate-backed, explicitly `AVAILABLE` provider, then locks its GPU and node before creating the attempt, two-minute lease, fencing token, `JOB_LEASED` outbox event, and `LEASED`/`BUSY` states. It enforces recipe minimum VRAM and one active job per provider node. A competing claim leaves the losing job queued.

`LeaseExpiryService` locks one overdue active lease and its related records with `SKIP LOCKED`, marks the lease expired, marks an active attempt `LEASE_EXPIRED`, moves an active job to `RETRY_WAIT`, takes the provider `OFFLINE`, and emits `JOB_LEASE_EXPIRED`. It never automatically retries or declares the GPU safe to reuse; a terminal attempt/job is not reopened. `LeaseAcknowledgementService` records an idempotent `ISSUED` to `ACKNOWLEDGED` receipt only for the authenticated, currently bound provider certificate, matching node and fencing token, unexpired lease, active attempt/job, and busy node. It emits one receipt outbox event; a receipt does not start work or extend the expiry.

`LeaseExpiryWorker` can poll this transaction when `HYPERLOOMS_LEASE_EXPIRY_ENABLED=true` is explicitly set on a normal control-plane process. It processes at most 64 leases per poll, each in a separate transaction, with a 5-second default fixed delay (`HYPERLOOMS_LEASE_EXPIRY_POLL_INTERVAL_MS`). It is disabled by default and forcibly disabled for operator CLI commands. Multiple workers rely on the transaction's `SKIP LOCKED` and event-key uniqueness; a database failure is surfaced to the scheduler and the next poll retries. This reconciles database state only: it cannot stop a remote process, prove the GPU is free, or resume a job.

`SchedulerClaimWorker` can invoke `claimNext` when `HYPERLOOMS_SCHEDULER_ENABLED=true` is explicitly set on a normal control-plane process. It processes at most 16 claims per poll, each in a separate transaction, with a 5-second default fixed delay (`HYPERLOOMS_SCHEDULER_POLL_INTERVAL_MS`). It is disabled by default and forcibly disabled for operator CLI commands. Competing instances rely on the claim transaction's row locks and uniqueness constraints. A database failure is not swallowed. Do not enable this experimental poller for real users: it can issue a lease and transport offer, but cannot command execution, renew a lease, or safely recover remote work.

`LeaseExecutionStateService` is internal-only and currently has no gRPC/HTTP caller. It accepts `LEASED -> STARTING -> RUNNING` only for the current active certificate-bound peer, acknowledged unexpired lease, matching fencing token, busy node, and matching attempt/job states. Duplicate progress reports are idempotent. A failure report from `STARTING` or `RUNNING` atomically marks attempt/job `FAILED`, lease `COMPLETED`, node `OFFLINE`, and writes one outbox event. Expired, revoked, wrong-node, or wrong-token reports are rejected. This does not run a container; successful completion is deliberately absent until result artifacts can be verified. An expiry transaction still quarantines a running lease, and a later failure report cannot overwrite its `RETRY_WAIT`/`LEASE_EXPIRED` outcome.

`LeaseExecutionPlanService` is another internal-only boundary with no gRPC/HTTP caller. In one database transaction it checks the authenticated active certificate, matching node and fencing token, acknowledged unexpired lease, leased attempt/job, approved recipe, verified GPU, and complete version-1 verified-input metadata. Only then does it return a snapshot of the image digest, runtime ceiling, GPU and private input prefix for a future command builder. Legacy version-0 fixtures cannot yield a plan. The returned snapshot is not a persistent command, S3 permission, runtime authorization, or protection against changes after the transaction; the future dispatch path must pin its contents and recheck fencing at execution and result completion. Live PostgreSQL tests cover the positive path, missing receipt, legacy job, wrong peer/token, revoked certificate, disabled recipe, and expired lease.

`LeaseExecutionCommandService` persists a single immutable command snapshot per acknowledged lease and writes `JOB_EXECUTION_COMMAND_PREPARED` in the same transaction. The snapshot pins the exact GPU UUID, image digest and verified input metadata. A retry returns the same command only while current authorization and all pinned bytes still match; a changed recipe is denied, not silently adopted. The outbox payload contains identifiers and the fencing token, not the private input prefix. V9 enforces one row per lease and rejects updates; append-only V10 pins the GPU UUID. The default-off gRPC staging path searches for a current unstaged lease, revalidates the authenticated peer and plan before sending, and records an idempotent agent staging receipt in V11 only when the command and fencing token still match. A prepared row can outlive expiry or revocation and is never authorization by itself. There is no outbox dispatcher or runtime caller; command delivery is direct and bounded to one per heartbeat.

`ScopedInputReadService` is an internal server-mediated read boundary. It requires the current certificate-bound lease, exact prepared command and staging receipt, and matching fencing token; it derives the S3 key from the verified snapshot rather than accepting a caller-supplied key or bucket. It validates the canonical manifest digest, file count and total size, checks that the requested path is listed, bounds the read, verifies the file hash and length, then rechecks the live lease and receipt before returning bytes. The default-off `AgentArtifactService.ReadInput` exposes only `request.json` over the required-mTLS listener, caps the file at 1 MiB, and rechecks authorization before each 32 KiB chunk. It gives no S3 credentials or presigned URL. The agent has a separate default-off reader that assembles strictly ordered, bounded chunks, checks the full-file SHA-256 and JSON, then discards the bytes after a verification log. Neither side interprets this read as permission to execute. Revocation or expiry after a sent chunk remains a distributed race, so execution and result acceptance must independently revalidate authorization.

The Go agent also has an internal-only Docker runtime foundation for Linux amd64: digest-only image reference, verified Cosign workflow identity, explicit GPU UUID, bounded memory/PIDs, no container network, read-only root, dropped capabilities, non-root UID, lease/runtime deadline, bounded JSON input/result file mounts, and cleanup after the container exits or the attached agent cancels. Docker's full returned container ID is used for start, wait, and removal. Created containers carry exact agent/node/lease labels. A bounded crash-recovery helper checks labels and lease-bound names before removing exact IDs; any mismatch stops the sweep. Enrolled-agent startup acquires a process-lifetime OS lock in its private state directory. Experimental `HYPERLOOMS_AGENT_RUNTIME_RECOVERY_ENABLED=true` runs recovery under that lock before connection; it defaults off pending Linux NVIDIA host qualification. The lock only serializes processes using the same state directory. The runtime is not connected to staged commands, has no lease renewal/stop or result upload, and does not prove isolation from a malicious image. Docker daemon access is itself privileged, and another daemon user can forge labels. Do not wire untrusted work until the execution lifecycle and a Linux NVIDIA host test pass. Jetson's ARM64/integrated-GPU path remains separate: an original Nano passed operator-reported host, root-container, and restricted non-root CUDA kernel smokes with cleanup, but has no schedulable GPU identity, lease-bound execution, artifact exchange, or remote results in Hyperlooms.

After an authenticated heartbeat, the gRPC stream offers an issued lease for that certificate-bound node. The Go agent checks identifiers, GPU, token and expiry, then atomically syncs a private local receipt journal before sending a transport receipt. A duplicate offer is idempotent; a conflicting unexpired lease is rejected. With `hyperlooms.agent.command-staging-enabled=true` and the agent's explicit staging capability, a later heartbeat can carry the prepared command. The agent requires a server-confirmed matching lease receipt, checks the command ID, job/attempt/node/GPU, fencing token, expiry, digest and bounded input metadata, then syncs it to the journal before sending a staging receipt. Neither server nor agent interprets staging as permission to run. There is no S3 grant, image pull, Docker invocation, lease renewal, active-lease cancellation, or verified result upload in this path. The claim poller remains experimental and disabled; the current system has no safe path to make a node `AVAILABLE`. A crash after receipt still leads to lease expiry and node quarantine if reconciliation runs. Runtime recovery and fencing checks on result completion remain required before activation.

## Provider enrollment boundary

`ProviderEnrollmentService` is internal-only. A trusted operator workflow can issue an invite for an owner subject, with a 5-minute to 24-hour lifetime, and revoke it before use. The token is randomly generated and only its SHA-256 digest is stored. Redemption locks the invite row so concurrent retries create exactly one node and one `PROVIDER_NODE_PENDING` outbox event. The same token can replay the resulting node ID, but it does **not** authenticate later agent sessions. No invite issuance or redemption HTTP endpoint is exposed.

`ProviderIdentityService` can register an expected, operator-approved certificate for a pending node. The certificate must contain exactly one provider URI SAN in the form `urn:hyperlooms:provider:<canonical-lowercase-uuid>` matching the node ID. Its DER SHA-256 fingerprint is stored; a different certificate or a claimed node ID alone is not enough. The opt-in gRPC listener requires client certificates signed by its configured CA and extracts the peer certificate from the authenticated TLS session. The stream then checks the exact stored fingerprint and node state before accepting a hello. An operator-only, no-listener CLI can issue/redeem invites, validate and bind CA-issued certificates, stage a replacement, and revoke a node. During rotation the old certificate stays active until the replacement authenticates; then the switch is atomic and the node remains offline. Production PKI issuance and operator SSO/RBAC are **not** implemented. Do not expose these internal methods through an unauthenticated endpoint. See [provider identity operations](../security/provider-identity-operations.md).

`ProviderCapabilityService` accepts a bounded protocol-v1 hello report only for an active certificate-bound peer. It cross-checks the claimed node ID, records GPU attributes as `REPORTED`, and keeps the node `OFFLINE`. An unchanged, previously verified GPU remains verified; changed attributes reset it to `REPORTED`, and a GPU missing from the report becomes `REJECTED`. The trusted local `inspect-gpu` command shows the current report and a deterministic fingerprint. After independently witnessing the host and retaining evidence, an operator can use `approve-gpu` to atomically bind that fingerprint and an evidence digest to a review record and set the GPU to `VERIFIED`. This requires an active certificate, fresh heartbeat, offline node, and unchanged `REPORTED` snapshot. It does **not** perform remote attestation, authenticate the named reviewer, validate the evidence content, or make the node `AVAILABLE`. The operator command must remain restricted until operator SSO/RBAC and evidence custody exist; reports alone never authorize scheduling.

## Submission boundary

`JobSubmissionService` accepts a trusted requester subject, a caller-generated idempotency key, and a `JobRequestV1` containing an approved recipe ID and lowercase SHA-256 digest of a future input manifest. The opt-in REST controller obtains that subject only from a verified JWT, never from client JSON. The service, not its caller, computes the canonical request hash. The exact UTF-8 bytes are `hyperlooms-job-request-v1\nrecipeId=<lowercase UUID>\ninputManifestSha256=<lowercase hex>\n`, including the final newline. The idempotency key and requester identity are scoped separately and are not hashed into the request body. A fixed test vector protects this representation from accidental drift. The service commits a version-1 `CREATED` job and `JOB_CREATED` outbox event together; a replay with the same requester/key requires the same version, recipe, manifest digest, and hash.

`CREATED` is not schedulable: the manifest digest is only a declaration, not proof of uploaded bytes. An opt-in, scope-gated requester API can submit, owner-read, stream bounded inputs, and queue version-1 jobs using OIDC/JWT. A loopback-only Keycloak development profile now issues real tokens; production identity-provider deployment is still absent, and this does not activate the scheduler. Scheduler tests also insert legacy version-0 `QUEUED` fixtures directly; that is not a production intake path. See the [requester API boundary](../security/requester-api.md).

The Python workload SDK can build deterministic input-manifest v1 bytes from regular local files and calculate their digest, with normalized relative paths, sorted entries, bounded manifest size, and local symlink rejection. The control plane has a strict, internal-only reader for those exact canonical bytes. It rejects malformed JSON, extra fields, noncanonical whitespace/numbers, unsafe or unordered paths, over-limit entry counts, and digest-format errors; a fixed cross-language test vector pins the SHA-256.

`InputSnapshotStager` is also internal-only. It reads a staged manifest and files from job-ID-scoped S3 keys, compares the manifest to the declared digest, enforces an 8 MiB per-file and 32 MiB total input cap, hashes the actual bytes, and copies those bytes to a new server-generated verified prefix. It reads the copy back and checks content again before returning the prefix. A real S3-compatible local round-trip test passes. The verified prefix must remain server-write-only.

`InputStagingService` provides a server-mediated path into those staging keys. The opt-in REST controller supplies only an authenticated issuer-scoped requester identity and bounds each upload body; the service checks the job owner, version, `CREATED` state, and recipe approval before touching object storage. It accepts only the canonical manifest matching the declared digest, enforces the aggregate and per-file limits, and accepts only files whose path, size, and digest match that manifest. S3 conditional `If-None-Match: *` puts make each staging key create-once; an identical retry is accepted, while a conflicting existing object is never overwritten. This does not issue presigned upload grants, provide a browser login, rate-limit requests, or enforce bucket-level immutability. A state change after the database check can leave an unused staging object, but queueing rechecks state under lock and verifies every byte.

`JobInputQueueService` takes the authenticated requester subject from the opt-in controller, verifies job ownership/version/recipe/state, stages outside the database transaction, then locks both job and recipe and checks them again. Only an unchanged version-1 `CREATED` job with an approved recipe can atomically record the verified prefix, digest, file count, byte count, `QUEUED` state, and one `JOB_QUEUED` outbox event. A retry of an already queued job returns its state without restaging. V8 database constraints reject a direct version-1 `QUEUED` row without verified input; legacy version-0 fixtures remain possible. The queue result deliberately does not expose the private object key. The experimental default-off scheduler worker can claim queued jobs, but there is no real GPU execution. Failed or racing stages may leave orphaned S3 copies; garbage collection and bucket-level write-once/immutability policy are still required. This is a tested opt-in intake transition, not a public-ready compute service.

`JobCancellationService` locks an owner-scoped version-1 job before changing `CREATED` or `QUEUED` to `CANCELED` and writing one outbox event. A repeated cancellation is idempotent. A scheduler claim racing with cancellation either sees the canceled state or obtains the lock first, after which the cancellation is rejected; the API never pretends that an issued lease or running container has been stopped. Active-lease cancellation remains blocked until agent stop, acknowledgement, and fencing are implemented.

## Protocol boundary

`proto/hyperlooms/agent/v1/agent_session.proto` defines a versioned hello, GPU capability report, heartbeat, issued-lease offer/transport receipt, separately gated prepared-command/staging-receipt exchange, and separately gated bounded input-read RPC. The offer carries no executable recipe or artifact access and does not start a job. A staged command is persisted by the agent; its acknowledgement is not execution authorization. The control plane exposes a disabled-by-default gRPC port with required mTLS and a 64 KiB inbound message cap. The Go agent can discover local NVIDIA GPUs and initiate the outbound stream when all TLS and node settings are supplied. Hello is required before other session messages; wrong node identity, unsupported protocol, malformed reports, and non-increasing heartbeat sequences are rejected. Heartbeats update `last_seen_at` only and **do not** turn a reported GPU or node into schedulable capacity. The scoped read streams one verified input file from server-side object storage, not arbitrary artifacts or credentials. Real-certificate, database-backed mTLS offer/receipt/staging/input-read tests passed locally on Windows with OpenSSL, using a simulated gRPC client rather than a real Go agent or GPU host. A real Linux NVIDIA host test is still required.

The provider product is installable software on a supported host, with a background Go service and an embedded local browser console; it is not a hosted web service that can access a stranger's GPU by itself. The separate requester/operator dashboard and control plane are hosted services. The agent initiates outbound mTLS connections, so contributors should not need to expose the console to the public internet. The eventual customer package needs a signed installer, supported updates, service management, and a safe first-run enrollment path; none is complete yet.

The agent currently serves a read-only console and status JSON on its local health port. Console routes require a loopback peer and Host header. They show locally discovered NVIDIA hardware, authenticated-session state, and bounded local connection/hardware events; they do not provide enrollment, private-key upload, workload controls, or public access. Local hardware discovery does not imply control-plane verification.

## Next implementation increment

The real-certificate mTLS staging test is in place, and the separately gated bounded input-read RPC is implemented. Next, retain verified input only for a lease-bound execution worker, implement safe lease renewal/stop, execution-state reports, and verified result upload with fencing at every boundary. Qualify real NVIDIA discovery and independently reviewed hardware on a supported Linux host, integrate production PKI, operator SSO/RBAC and evidence custody, and implement safe, revocable availability transitions. Promote the loopback-only Keycloak path to production-grade identity, approve the signed PyTorch recipe by exact digest, and add production ingress/storage controls. Keep scheduler polling and runtime execution off until those gates pass. Jetson Nano's restricted CUDA smoke is hardware evidence, not Hyperlooms remote-job qualification.
